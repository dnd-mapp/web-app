# Workspace

## Angular workspace

```bash
pnpm ng version
```

The repository is an [Angular CLI](https://angular.dev/tools/cli) workspace, configured in [angular.json](../angular.json). It holds a single project, the `web-app` application under [projects/web-app](../projects/web-app), and that is by design: this repository is the web frontend and nothing else. The CLI is configured to use pnpm for the packages it installs, and its usage analytics are turned off. Angular, its CLI and TypeScript share the `angular` catalog in [pnpm-workspace.yaml](../pnpm-workspace.yaml), so they move together on upgrades.

## TypeScript configuration

[tsconfig.json](../tsconfig.json) carries the compiler options the project extends, with every strictness flag TypeScript offers turned on, plus the `@/<area>` path aliases that map onto the barrel files under `projects/web-app/src`. [tsconfig.tooling.json](../tsconfig.tooling.json) is referenced from it as well and covers the JavaScript tooling files at the root, under `scripts` and in each project, such as the ESLint configs. They are checked with `checkJs` and the Node.js types from `@types/node`, so the `// @ts-check` header in each of them is type-checked in the editor. TypeScript 6 no longer loads every package under `node_modules/@types` on its own, so the `types` entry is what brings the Node.js types in; the project tsconfig files keep them out of the browser code.

Within the project, [tsconfig.app.json](../projects/web-app/tsconfig.app.json) covers the application code, [tsconfig.spec.json](../projects/web-app/tsconfig.spec.json) covers the specs and the `testing/` folders, and [tsconfig.e2e.json](../projects/web-app/tsconfig.e2e.json) covers the end-to-end tests and the Playwright config with the Node.js types. The type-checked ESLint rules read types through the TypeScript project service, so every TypeScript file has to be included by one of them; [TypeScript and JavaScript](linting.md#typescript-and-javascript) spells out the consequences.

## Application layout

The `web-app` application lives under `projects/web-app/src`, divided into areas. `core` holds what bootstraps the application: the root component, the top bar this application fills, and its configuration. `pages` holds the pages the router renders, one folder per page, such as the home page at the root path. `auth` holds what accounts and access are built from, with `auth/components` holding the components that offer an account action, such as the buttons to log in and to sign up. `shared/components` holds the components any page may use, such as the bar across the top, and the ones that dress up a native element through an attribute selector, such as the button. `shared/localization` holds the texts the interface is written in and the providers that resolve them, described in [Localization](localization.md). `shared/testing` holds the helpers specs share, described under [Unit tests](testing.md#unit-tests); it is a `testing/` folder itself, so it stays out of the application build. Each area exposes its public symbols through an `index.ts` barrel, and `paths` in `tsconfig.json` maps an alias onto that barrel, so code outside the area imports from the alias rather than through a relative path. An alias is the area's path behind a prefix that says who owns it: `@/` for the application's own areas, as in `@/core` and `@/pages`, and the package name for an area written to be lifted out, as in `@dnd-mapp/auth/components` and `@dnd-mapp/shared/components`. The second form is the name each area will publish under, so lifting one out leaves every import as it is: its entry under `paths` goes away and a dependency takes its place. A new area is complete once it has a barrel and an alias for it, plus a `.../testing` alias when it ships harnesses. Which area a component belongs in follows from who could reuse it. `core` and `pages` are this application, so a component that only makes sense here, such as the top bar holding its account actions, lives in `core` beside the root component that renders it. `auth` and `shared` are written to be lifted out into packages of their own once a second application needs them: `auth` holds what authentication and authorization are built from, and `shared` holds what any application or library may reuse, `auth` included. That gives the areas one direction of dependency, which imports hold to: the application reads from `auth` and `shared`, `auth` reads from `shared`, and `shared` reads from neither. An import that would point the other way says the code is in the wrong area. A component the router renders at a URL of its own is a page and lives under `pages`, whatever else it holds. File and class naming follows the `schematics` defaults in `angular.json`: `root.component.ts` holds `RootComponent`, styles are SCSS, and guards, interceptors, pipes and resolvers use a `.` type separator. Beside the areas, one folder holds no TypeScript and so has no barrel or alias: `design-system`, which holds the SCSS described in [Design system](design-system.md). It is written to be lifted out as well, into the package the applications and the libraries both load their tokens from, so a stylesheet reaches it through `styles.scss` rather than naming the folder itself.

## Routing

The router renders the page of the current URL into the `router-outlet` in [root.component.html](../projects/web-app/src/core/root/root.component.html), inside the `main` region the shell lays out. [app.routes.ts](../projects/web-app/src/core/config/app.routes.ts) holds the routes and [app.config.ts](../projects/web-app/src/core/config/app.config.ts) hands them to `provideRouter` as the application bootstraps. The home page sits at the root path; every page that follows gets a path of its own in that array, so the outlet has one place to read from.

A route names its component directly rather than loading it on demand. The route a visitor lands on is on the critical path by definition, so splitting it off defers nothing. Building the home page as a chunk of its own left the initial bundle larger than it is now. The split costs more in module plumbing and lost compression than the page weighs, and the chunk is fetched right away regardless. A page a visitor reaches by navigating is the other case. It switches to `loadComponent` for itself alone once it carries weight the pages before it should not pay for. Which page a URL resolves to is bootstrapping rather than component behavior, so an end-to-end test covers it, as [End-to-end tests](testing.md#end-to-end-tests) describes, and the shell's own spec provides the router with no routes at all.
